# 상용급에 근접한 오프라인 한국어 검사기 설계

## 배경

GeulLint v0.3.0-alpha.2는 브라우저, CLI, LSP, VS Code에서 같은 Rust 규칙 엔진을 사용하고 문장을 외부 서버로 보내지 않는다. 릴리스 자동화, 다중 플랫폼 산출물, 체크섬, SBOM, attestation도 이미 갖췄다.

그러나 현재 정확도 엔진은 116개 공개 규칙, 표면형 matcher, 일부 생산적 규칙이 중심이다. 형태소 분석은 선택 기능이며 실제 진단의 공통 기반이 아니고, 범용 미등록어(OOV) 후보 생성과 문맥 순위화가 없다. 저장소 자체 회귀 코퍼스는 구현 회귀를 막지만 일반 한국어 정확도를 입증하지 않는다. 따라서 규칙 수만 늘려서는 상용 검사기에 근접할 수 없다.

## 목표

사용자가 데이터, API 키, 수동 검수, 로컬 명령 실행, 패키징 또는 GitHub 배포를 담당하지 않아도 다음을 완성한다.

- 맞춤법, 띄어쓰기, 조사, 활용, 문법, 제한적 문체 진단
- 범용 오타에 대한 문맥 기반 후보 제시
- 자동수정과 검토 제안을 엄격히 분리하는 안전 정책
- Native, WebAssembly, VS Code의 동일한 최종 진단 계약
- 최초 자산 설치 뒤 문장 전송 없이 완전 로컬 검사
- 재현 가능한 데이터, 모델, 사전, 품질 보고서와 릴리스

목표는 규칙 개수가 아니라 독립 실문장 지표다. 게이트를 넘기 전에는 README와 홍보물에 `상용급`, `Harper급`, `네이버급`을 쓰지 않는다.

## 검토한 접근법

### 규칙과 사전만 확대

작고 빠르며 설명하기 쉽지만, 새로운 오타와 문맥 의존 띄어쓰기, 생산적 활용의 재현율 상한이 낮다. 기존 고신뢰 규칙을 유지하는 용도로만 사용한다.

### 생성형 문장 교정

재현율 잠재력은 높지만 문장을 임의로 재작성할 수 있고, 정확한 오류 범위와 설명, 결정성, WebAssembly 크기, 안전 자동수정에 불리하다. 기본 엔진으로 사용하지 않는다.

### 제한된 후보 생성과 소형 문맥 랭커의 하이브리드

결정론적 엔진이 허용된 수정 후보만 만들고 소형 로컬 모델은 후보 순위와 신뢰도만 계산한다. 원문 범위를 보존하면서 규칙 엔진보다 넓은 재현율을 얻고, 생성형 교정의 임의 재작성을 막을 수 있다. 이 방식을 채택한다.

## 엔진 설계

```text
소스 보호 범위
  -> 문장·어절·음운 분석
  -> 형태소 격자
  -> 규칙·철자·활용·조사·띄어쓰기 후보
  -> 결정론적 1차 필터
  -> GeulRank-small 문맥 순위화
  -> 오류 유형별 신뢰도 보정
  -> Safe / Review / Abstain
  -> 충돌 없는 편집 계획
```

- `source`: Markdown 코드, 문자열, URL, 경로 등 검사 제외 범위를 보존한다.
- `analysis`: 어절 전체에 품사 하나를 붙이는 현재 구조를 어간, 어미, 조사, 원형, 불규칙 활용의 복수 분석 격자로 바꾼다.
- `lexicon`: 표면형, 원형, 품사, 빈도, 고유명사 성격, 출처를 가진 압축 FST/DAWG를 사용한다.
- `candidate`: 초중종성 가중 편집거리, 두벌식 인접 키, 자모 합성, 삽입·삭제·치환·전도, 음운 혼동, 활용, 조사 이형태, 2~4어절 결합·분리를 다룬다.
- `ranker`: 앞뒤 문맥과 표시된 오류 범위, 후보, 형태소 feature만 점수화하며 새 문장을 생성하지 않는다.
- `policy`: 유형별 임계값과 독립 코퍼스 근거로 Safe, Review, Abstain을 정한다.
- `planner`: 겹치는 편집을 전역 점수로 선택하고 수정 후 재검사와 멱등성을 보장한다.
- `trace`: 규칙, 사전, 형태소, 모델 중 어떤 근거로 제안했는지 공개 API에 기록한다.

## 모델과 배포 프로필

`GeulRank-small`은 8K~16K 한국어 subword/자모 어휘, 6개 encoder layer, hidden size 약 256, 10~15M parameter의 후보 cross-encoder로 설계한다. 최대 32개 후보를 결정론적 필터가 6~8개로 줄인 뒤 한 번에 점수화한다. INT8 양자화 후 모델은 12~18MB를 목표로 한다.

두 배포 프로필을 명확히 분리한다.

- `compact`: 지금의 초경량 규칙 엔진. 빠른 CI와 제한 환경용이며 상용급 정확도를 주장하지 않는다.
- `standard`: 압축 형태소·어휘 자산 12~20MB와 INT8 모델 12~18MB를 포함하는 기본 사용자 제품이다.

웹은 standard 자산을 Worker에서 최초 한 번 받아 Service Worker에 캐시한다. 이 다운로드는 엔진 설치이며 사용자 문장이나 사용 통계는 전송하지 않는다. Native와 Web은 같은 모델 버전, 후보 규칙, 정책 임계값을 사용하고 10,000문장 패리티 게이트로 결과를 고정한다.

## 데이터와 평가

필수 경로는 계정, 본인 인증, API 키, 약정 서명이 필요 없는 공개 자료만 사용한다. 출처, 버전, 라이선스, SHA-256, 문서 ID를 manifest에 기록한다. 조건이 불명확해진 자료는 자동 제외한다.

- 독립 다중참조 평가는 KoLLA v2 같은 공개 인간 교정 자료를 저장소 밖 격리 경로에서 사용한다.
- 정상문 학습과 오탐 스트레스 검사는 Tatoeba 한국어 문장, 허용된 위키미디어 덤프, 허용 라이선스 오픈소스 문서를 사용한다.
- 실제 수정 패턴은 허용된 위키 revision과 문서 commit의 짧은 국소 수정에서 추출한다.
- 사전은 Apache-2.0 mecab-ko-dic과 출처별 허용 여부를 검증한 현대 어휘 자료로 빌드한다.
- 합성 오류는 학습과 회귀에만 사용하며 공개 정확도 수치에는 넣지 않는다.

분할은 문장 생성 전에 출처, 문서, 작성자 단위로 수행한다. 정규화 해시, 자모 5-gram MinHash, 의미 유사도 검사로 train/dev/test 누수를 차단한다. final holdout의 문서 ID와 해시는 엔진 변경 전에 고정하고, 최종 후보에서만 집계 지표를 실행한다.

평가는 세 층으로 공개한다.

1. 저장소 자체 회귀: 코드 회귀만 판단한다.
2. 공개 독립 benchmark: 재현 가능한 비교 수치를 제공한다.
3. 잠긴 release holdout: 출시 승격만 판단하며 학습과 임계값 조정에 사용하지 않는다.

상용급 근접 판단에 쓰는 전체 평가 풀은 최소 20,000개의 서로 다른 자연 문장으로 구성한다. 이 안에는 독립 인간 교정에서 얻은 오류 edit 5,000개 이상, 실제 정상 문장 10,000개 이상, 8개 이상 장르가 있어야 한다. KoLLA 같은 전문가·다중참조 subset과 revision에서 얻은 인간 수정 subset은 수치를 합쳐 숨기지 않고 각각 별도 행으로 보고한다. 주요 장르는 오류 edit 250개 이상, 홍보하는 오류 유형은 50개 이상을 확보한다.

## 출시 품질 게이트

상용급 근접 표현은 서로 다른 잠긴 holdout 두 개를 연속으로 통과한 뒤에만 허용한다.

| 항목 | 최소 기준 |
| --- | ---: |
| 기본 진단 micro precision | 98% |
| 기본 진단 recall | 85% |
| 검토 제안 precision | 95% |
| 철자 후보 top-1 / top-5 | 92% / 98% |
| 정상 문장 specificity | 99.5% |
| Safe fix precision의 Wilson 95% 하한 | 99.5% |
| 오류 유형별 recall 최저값 | 80% |
| 장르별 recall 최저값 | 75% |
| calibration ECE | 0.05 이하 |
| 범위 보존·멱등성·Native/WASM 계약 | 100% |

홍보하는 오류 유형은 독립 인간 수정 표본 50개 이상을 가져야 한다. 근거가 부족하거나 유형별 게이트를 못 넘으면 `experimental` 또는 `review`로 강등한다. 고유명사, 신조어, 외래어, 인용, 숫자, 문체 교체는 모델 점수가 높아도 기본 자동수정 대상이 아니다.

성능 예산은 standard 기준으로 1,000자 warm p95 Native 80ms, Web 200ms, 증분 한 문장 Native 25ms, Web 60ms, Native warm memory 180MB, 브라우저 Worker 220MB, 최초 웹 자산 40MB 이하로 둔다.

## 제품 계약

- 웹: 원문·교정문 대응 강조, 수정별 적용·거절, 안전 수정 전체 적용, 다단계 undo/redo, 사용자 사전, TXT/Markdown 입출력, PWA 설치와 오프라인 준비 상태를 제공한다.
- VS Code: 증분 분석, Fix All Safe, preview, 사전 추가, 범위별 무시, 규칙 설명, 대문서 취소와 캐시를 제공한다.
- CLI: `check`, `fix --diff`, `--stdin`, `--changed`, `--watch`, `init`, `doctor`, 사전 관리, 원자적 파일 교체와 안정적인 JSON/SARIF 계약을 제공한다.
- 공통: 진단 범위, 원문, 후보, 이유, 근거, 신뢰도, 안전 등급, 규칙 문서 링크를 같은 스키마로 노출한다.

자동 텔레메트리는 넣지 않는다. 피드백은 사용자가 명시적으로 선택한 최소 문장과 버전 정보를 로컬 파일로 내보내고, 내용을 확인한 뒤 GitHub Issue 작성 화면을 여는 방식만 제공한다.

## 배포와 주장 정책

Windows, macOS, Linux의 6개 OS/CPU 아카이브, npm launcher, VSIX, 웹 PWA, 체크섬, SBOM, attestation을 유지한다. 모델과 사전도 별도 manifest, 모델 카드, 데이터 카드, 라이선스, SHA-256, 재현 빌드 명령을 제공한다. 실행 파일 하나를 전면에 내세우지 않고 오픈소스 저장소의 일반적인 아카이브·패키지·VSIX·웹 배포 문법을 유지한다.

네이버 등 상용 서비스의 비공식 API나 웹 화면을 스크래핑하지 않는다. 공식적이고 재현 가능한 비교 경로가 없으면 제품명 상대 비교를 하지 않고 독립 gold 수치만 공개한다.

## 비목표

- 규칙 800개 같은 개수 목표
- 서버에 문장을 보내는 검사 API
- 대형 생성 모델이 문장을 자유롭게 다시 쓰는 교정
- 근거 없는 100% 정확도 또는 상용 제품 동급 주장
- 계정, 유료 인증서, 수동 약관 승인에 의존하는 필수 설치·평가 경로
